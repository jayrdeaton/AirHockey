# AirHockey

A digital AirHockey game (Expo/React Native, Skia-rendered). Part of the `@rific`/`@tastic`/InfiniteToken app ecosystem - depends on `@rific/auto-paper`, `@rific/feedback-press`, `@rific/splash-gate`, `@rific/toaster`, `@rific/updater`, `@tastic/achievements`, `@tastic/core`, `@tastic/edge-guard`, `@tastic/hud`, `@tastic/input`, `@tastic/physics`, `@tastic/profile`, `@tastic/split-screen`, `@tastic/sprites`.

**Expo has changed.** Read the exact versioned docs at https://docs.expo.dev/versions/v57.0.0/ before writing any code - don't rely on general Expo knowledge, this app is on SDK 57 specifically.

## Commands

```bash
npm run lint          # expo lint .
npm run fix            # expo lint . --fix
npm test               # Jest (12 suites, 164 tests)
npm run test:watch     # Jest --watchAll
npm run typecheck      # tsc
npm run verify         # lint + test + typecheck
npm run doctor         # expo install --fix && expo-doctor
npm start              # Expo dev server
npm run client          # Expo dev server (dev client build)
```

Always run `npm run lint` before finishing any task. This is an app (`"private": true`, no publish scripts) - `verify` doesn't include a build step.

**Builds and OTA updates:** the `build` and `update` scripts are plain `eas build` and `eas update`, with profiles in `eas.json` (`development`, `preview`, `production`). Pass the profile through, e.g. `npm run build -- --profile preview` or `npm run update -- --branch production --environment production --message "..."`. Nothing in them runs `verify`, so run `npm run verify` first. An OTA update also bumps `otaVersion` in `src/constants/release.ts` (the version label players see), committed before publishing. They used to be `@rific/updater`'s `rific-updater-build`/`rific-updater-update` bins, which @rific/updater 0.7.0 removed; the package stays for its OTA update hook.

## Fleet package extraction (2026-09-17)

A fleet-wide audit today (AirHockey + BoxHockey + Pong + LightCycles + Snake) went looking for game-shell code duplicated across all five apps. Auditing `RotationAwareStatusBar` - one of the duplicates - turned up a real bug specific to this app: `_layout.tsx`'s own copy called `useOrientationState()` with no argument, so the real OS status bar always tracked live device tilt regardless of this app's "Lock Orientation" setting, unlike every screen's own call (`index.tsx`, `loadout.tsx`, `game.tsx`'s `roundSettings.lockOrientation`) which already respected it. BoxHockey's copy had already threaded `locked` through correctly, so it became the reference the other four (including this one) were brought in line with - and since all five apps had hand-rolled the exact same ~10-line component independently, it was pulled straight into `@tastic/core` as `RotationAwareStatusBar({ locked })` right after, rather than fixing each app's local copy in place and extracting separately later. `_layout.tsx` now wraps the shared component in a local `ConnectedRotationAwareStatusBar` that reads `settings.lockOrientation` from `GameSettingsProvider` (an ancestor of `RootLayout`'s own body, not a descendant of it, so the shared component can't reach that context directly) and threads it through as `locked`. **Superseded 2026-10-07:** per-call-site locking is gone and so is `ConnectedRotationAwareStatusBar`; see Lock Orientation below.

Four more duplicated pieces found in the same pass moved into shared packages the same way:

- **`PlayerSetupPanel`** - was `src/components/PlayerSetupPanel.tsx` (now deleted), moved into `@tastic/hud`. Its old control-scheme-specific props (`controlScheme`/`onControlSchemeChange`/`controlSchemeOptions`/`otherControlScheme`) are gone, replaced by a generic `secondPicker`/`secondPickerId` slot - `loadout.tsx` assembles that slot itself, rendering `@tastic/hud`'s own separately-exported `ControlSchemePicker` into it and wiring it to this app's `settings.controlScheme` state, rather than `PlayerSetupPanel` knowing anything control-scheme-specific internally.
- **`HeroTitle.tsx`**'s staggered-letter wordmark animation - the local `AnimatedLetter`/`Word` helpers and their `STAGGER_MS`/`LETTER_DURATION_MS` constants are gone, replaced by `@tastic/hud`'s `StaggeredWord` component and `getStaggeredWordDuration` helper.
- **`Providers.tsx`**'s `FeedbackBridge` now calls `@rific/feedback-press`'s new `useFeedbackBridgeProps` hook to assemble the `FeedbackPressProvider` prop bag, instead of hand-listing `initialValue`/`onChange`/`soundInitialValue`/`onSoundChange`/`sound` itself.
- **`achievementEngine.ts`** shrank to a thin re-export via `@tastic/achievements`' new `createAchievementBindings(ACHIEVEMENT_CATALOG, getProfileStatsView)` factory - same exported names (`evaluateUnlockedIds`, `evaluateUnlockedIdsForProfile`, `unlockedKey`), so no call site changed.
- **`profileSelectionSlice.ts`** shrank to a thin re-export via `@tastic/profile`'s new `createProfileSelectionSlice<Player>('airhockey', defaultProfileSelectionState)` factory - same exported names (`profileSelectionActions`, default reducer).

Unrelated to the extraction itself but touched in the same working-tree pass, so noted here rather than left to be rediscovered later:

- **`redux/seatColorsSlice.ts`** gained a `profileOverride: Record<Player, string | null>` field (plus a `setProfileOverride` action) - a real gap, not a refactor. A manual recolor/clash-swap landing on a profile-selected seat in `loadout.tsx` previously only ever painted the live theme snapshot directly, so it evaporated the moment the screen's own color-reconciliation effect re-derived the seat's color from scratch - leaving and returning to `/loadout`, or a relaunch, silently reverted it to the profile's saved color. `profileOverride[seat]` now persists that override through Redux until the seat's own profile selection genuinely changes (`handleP1ProfileSelect`/`handleP2ProfileSelect` clear it first, before the new selection takes over). **Superseded 2026-09-18:** this file is now a thin binding over `@tastic/profile`'s new `createSeatColorsSlice<Player>('airhockey', defaultSeatColorsState)` factory rather than a hand-rolled reducer - see that package's own CLAUDE.md for the factory's full history (including its own `REHYDRATE` fix, which this app inherits for free).
- **`hooks/useGameSettings.tsx`** now merges a persisted settings blob onto `DEFAULT_SETTINGS` *before* validating it, rather than validating the raw blob. `isValidSettings` has no partial-merge path, so a blob written before some `GameSettings` field existed was missing that field entirely and used to fail the all-fields check over that one missing field alone - silently discarding every other still-valid preference in the same blob the moment a new setting shipped. A field the blob does provide with the wrong type still fails validation and rejects the merge outright, same as before.
- **`_layout.tsx`**'s `<Toaster />` now passes `historyButton={null} clearButton={null} limit={3}` explicitly - this app has no history-modal use case for `Toaster`'s history/clear controls to open, so leaving them on would add a stray control row above the toast stack for a feature that goes nowhere; `limit` is already the package's own default (3), pinned explicitly so it stays 3 regardless of what that default does in a future `@rific/toaster` version.

**Verifying the above live in a browser (not just Jest) turned up a real, separate bug in `@rific/core` - a genuine React "Cannot update a component (`Theme`) while rendering a different component (`Provider`)" warning on `/loadout`, traced to `createSettingsContext`'s `set()` calling the consumer's `onChange` *inside* the `useState` updater passed to `setSettings`.** A `useState` updater must be pure - React can invoke it outside the originating `set()` call (e.g. replaying a queued update while resolving a later render of the very same Provider) - and when that happened here, `onChange` (which `Theme.tsx` wires straight to `dispatch(themeActions.initialize(...))`) fired synchronously mid-render of an unrelated component. This factory backs `@rific/auto-paper`'s `Theme`, `@rific/feedback-press`'s haptic/sound settings, and `@rific/scroll-view`'s settings context alike, so the bug (and the fix) reaches all three. The same audit found the identical shape independently duplicated, not through this factory, twice more inside `@tastic/core`: `createGameSettingsProvider`'s `setSettings` called `AsyncStorage.setItem` from inside its own updater, and `OrientationProvider`'s `set` called the consumer's `onLockChange` the same way - both used by this app (`GameSettingsProvider`/`OrientationProvider` in `_layout.tsx`). All three were fixed the same way: the side effect moved into a `useEffect` keyed on the settled state, skipping the mount-time run so the contract (onChange/persistence only fires for a real `set()` call, never for `initialValue`/`defaultSettings` seeding) is unchanged. Confirmed fixed by clearing this app's own web `localStorage` and reloading `/loadout` directly - the warning no longer reproduces. Now on `@rific/core@0.1.2` and `@tastic/core@0.5.1` (both patch bumps, no API change).

**Same pass also found and fixed a real gap in `@infinitetoken/jest-config`'s `knownSubpathMocks`:** it stubbed `@rific/feedback-press/audio`'s `useAudioPool` but not `useGatedAudioPool` - a real risk for this app specifically, since `hooks/useGameSound.ts` re-exports `useGatedAudioPool` directly, and any future test rendering a component that calls it would have hit real `expo-audio`/native audio APIs during a Jest run instead of the intended inert stub. Fixed by adding the same inert-hook stub for it. Now on `@infinitetoken/jest-config@0.3.1`.

**`@tastic/hud@0.9.0` closed the `PlayerSetupPanel` CPU-difficulty alignment gap this app's own earlier migration agent found blocked (no override prop existed at all for the panel's internal `LabeledDropdown`) - `loadout.tsx`'s `p2Panel` now wires the new `cpuDifficultyAlignOverride` prop via `useZoneClampedAlign(p2Host.openId === getCpuDifficultyPopoverId('p2'), LABELED_DROPDOWN_POPOVER_WIDTH, getLabeledDropdownContentHeight(AI_DIFFICULTY_OPTIONS.length))`.** Confirmed, from the actual render tree (not assumption), that this is a documented no-op for this app: `p2Panel`'s CPU seat only exists in `vsCpu` mode, which always renders through the plain stacked `View` branch below, never `<DualZoneLayout>` (only `gameMode === 'twoPlayer'` gets a real `@tastic/split-screen` zone) - so `useZoneBounds()` is null there and `useZoneClampedAlign` falls straight back to `useAutoAlign`'s own plain screen-edge placement, same conclusion LightCycles' own `lobby.tsx` already documented for its identical seat before this prop existed. Wired in anyway, for parity with every other zone-aware popover in the fleet and so it starts clamping for free if `vsCpu` is ever nested inside a zone later. `npm run verify` (125/125 tests) stayed green.

- **`achievements.tsx` didn't rotate with the rest of the app.** Every other screen wraps its content in `FakeLandscapeView`/`rotateInsets`/`useRotation` (from `@tastic/core`) so it visually rotates to match a face-to-face seat's own orientation - `achievements.tsx` was the one screen still rendering screen-fixed. ## Fleet-wide drift audit round 3 (2026-09-18)

A third fleet-wide scan found a real bug in `loadout.tsx`: **`colorAlignOverride` was never wired to either color picker, even though `PlayerSetupPanel`/`InlineColorPicker` already supported it (the same plumbing `cpuDifficultyAlignOverride` uses).** Unlike the CPU-difficulty picker (a confirmed no-op everywhere in the fleet - it never actually renders inside a live split-screen zone), both p1's and p2's color pickers genuinely render inside a live `@tastic/split-screen` `DualZoneLayout` zone in two-player mode, so an unclamped popover could pick a vertical direction that overflows past the zone's shared-row boundary into the other player's own half. Unlike `cpuDifficultyAlignOverride` (gated behind `p2IsHuman`), both are wired unconditionally: every seat always has a color picker, human or CPU. `npm run verify` (125/125 tests) stayed green.

## Second fleet package extraction (2026-09-18)

Eight more pieces of duplicated code across this app and its siblings (Snake, BoxHockey, Pong, LightCycles) were extracted into shared packages, landing this app on `@rific/core@0.1.4`, `@tastic/achievements@0.1.2`, `@tastic/hud@0.11.0`, `@tastic/profile@0.6.0`, `@tastic/core@0.7.0`, and `@rific/auto-paper@0.11.1`:

- **`safeBack`** moved from a hand-rolled ~11-line function in `src/utils/navigation.ts` into `@rific/core`'s new `safeBack()` + `configureNavigation()`. `@rific/core` has zero dependency on `expo-router` by design (it works with or without any particular router), so the real `router` object is injected once via `configureNavigation({ router })` rather than imported inside the package - the same `OptionalModule`/`createModuleConfig` convention `@rific/scanner`/`@rific/resizable-input` already use for their own injected peers (expo-camera, react-native-paper). `@rific/core` mirrors only the three methods it actually calls (`canGoBack`/`back`/`replace`) as a local `SafeBackRouter` type rather than importing `expo-router`'s real types. `src/utils/navigation.ts` is now the 5-line thin re-export: `import { router } from 'expo-router'; import { configureNavigation, safeBack } from '@rific/core'; configureNavigation({ router }); export { safeBack }` - every existing call site (`safeBack()`, `onBack={safeBack}`, `onConfirm={safeBack}`) needed zero edits, since `safeBack` kept its exact zero-argument signature specifically so it keeps working as a bare callback reference. Pre-existing gap this extraction didn't fix: this app's own `src/__mocks__/expo-router.ts` still has no `canGoBack` field, so a test that actually exercised the fallback branch would throw against the mock today - no current test does, but it's worth knowing before adding one.
- **`achievement-state-pipeline`**: `useGameStats.tsx`'s per-seat achievement-unlock translation and `game.tsx`'s device-wide-unlock broadcast now call `@tastic/achievements`' new pure `mapUnlocksBySeat`/`broadcastDeviceUnlocks` helpers instead of two hand-rolled loops. This app adopts both as a pure drop-in - `recordMatchOutcome` now reads `mapUnlocksBySeat([1, 2] as Player[], context.profileIds, result.profiles)` (`useGameStats.tsx`), and the two-player branch of the `gameOver` effect in `game.tsx` reads `broadcastDeviceUnlocks([1, 2] as Player[], result.profiles, result.device)` before `setSeatUnlocks`. Both helpers preserve the order every call site already depended on (a seat's own profile-scoped unlocks before any device-wide ones get appended) - that's display/toast order, not incidental.
- **`quit-confirmation`**: `game.tsx` now uses `@tastic/hud`'s new `useQuitConfirmation` hook for the "Quit Match?" flow, replacing the local `confirmBackVisible` `useState` + hand-rolled `onBackPress`. This is worth documenting precisely because the hook's shipped signature is **not** what its first design proposed: `useQuitConfirmation` takes a lazy `hasProgress: () => boolean` getter, not a plain boolean - a correction made after AirHockey (along with BoxHockey and Pong) hit a real circular render dependency trying to adopt the original plain-boolean version. `paused` (`settingsOpen || confirmVisible`) has to be computed and handed into `useGameState()` as an input *before* that call returns the very `scores` state `hasProgress` needs to read, so a plain-boolean argument computed from `scores` at the hook call site literally cannot be evaluated in time. The hook now mirrors both `hasProgress` and `onConfirmedBack` into refs via an effect and reads them only inside `requestBack()`'s own closure, deferring the read to call time instead of render time. For this app, adopting the corrected hook required no bespoke per-app workaround beyond the one-line change already visible at the call site - `const { confirmVisible, requestBack, cancelBack } = useQuitConfirmation(() => scores[0] > 0 || scores[1] > 0, safeBack)` (`game.tsx`, right above `useGameState`) - with a doc comment there spelling out the same ordering constraint so a future reader doesn't try to "simplify" it back to a plain boolean. `paused` and the `ConfirmDialog`'s `visible`/`onCancel` props were updated to `confirmVisible`/`cancelBack` accordingly; `onConfirm` stays `safeBack` directly, unrelated to the hook.
- **`achievements-scaffolding`**: `achievements.tsx`'s local `MS_PER_DAY`/`startOfDay`/`unlockedLabel` day-diff helpers, its `ACHIEVEMENT_CATALOG.map()` loop, and its `<StatSection label='ACTIVITY'>` block are gone, replaced by `@tastic/achievements`' new headless `getAchievementCatalogRows()` and `@tastic/hud`'s new `<AchievementCatalogSection>`/`<ActivityStatSection>` components - `getAchievementCatalogRows(ACHIEVEMENT_CATALOG, stats, statsView, unlockedAchievements, effectiveProfileId)` feeds `<AchievementCatalogSection rows={...} />` directly. The split mirrors the existing `AchievementRow`/`achievementEngine` boundary on purpose: row computation stays in `@tastic/achievements` (headless, no JSX, no new RN peer deps), rendering stays in `@tastic/hud`. This is the first time `@tastic/hud` takes `@tastic/achievements` as a real peer dependency, and it's worth confirming precisely what state that landed in: `@tastic/hud`'s `AchievementCatalogSection.tsx` now does `import type { AchievementCatalogRow } from '@tastic/achievements'` - the real, type-only import - not the locally-duplicated `AchievementCatalogRow` interface that component briefly carried during its own implementation, before `@tastic/achievements` had actually shipped `catalogRows.ts`. The OVERALL/GOALS/VS CPU/TWO PLAYER (LOCAL)/PLAYER RANKINGS sections in `achievements.tsx` stay local and untouched, since those metrics are genuinely per-app.
- **`profiles-screen`**: `profiles.tsx` shrank from ~57 lines to a 34-line thin route around `@tastic/profile`'s new `<ProfilesScreen>` component, which now owns the container view, theme-derived bg/fg, the back button, and the commit-pending-edit-before-navigate composition every app used to hand-roll directly around `ProfilesManager`. AirHockey is one of the three apps (with Snake and Pong) whose adoption needed no special-casing at all - `onCreate={(patch) => createProfile(patch)}` works unchanged because this app's `Profile`/create-patch shape already *is* `@tastic/profile`'s own base type (unlike BoxHockey/LightCycles, which compose an extra `controlScheme`/`keyScheme` field onto the patch at their own call sites), and `defaultColor={defaultColors[0].value}` reads straight from `@rific/auto-paper` like every app but LightCycles (which uses its own local color constant). `ProfilesScreen` deliberately still doesn't call `useProfiles()`/`useGameStats()` itself, since those hooks' shapes are genuinely app-specific - this route still owns wiring `onDelete` to both `deleteProfile(id)` and `removeProfileStats(id)`.
- **`layout-corner-flash`**: `_layout.tsx`'s `AppStack()` now calls `@tastic/core`'s new `useThemedRootBackground(dark, false)` hook in place of the module-level `SystemUI.setBackgroundColorAsync('#000000')` call plus its own live-theme-tracking `useEffect`/`contentStyle` literal - `return <Stack screenOptions={useThemedRootBackground(dark, false)} />` is now the entire function body. The hook returns the full `screenOptions` object (`headerShown`, `gestureEnabled`, `contentStyle`), keeping `gestureEnabled` as a caller-supplied parameter rather than a hardcoded value inside the hook, since disabling it addresses a separate concern (iOS's native swipe-back gesture fighting `TouchInputLayer`'s own Pan gestures) that doesn't apply to every possible consumer. This app still passes `false` with no rationale comment at the call site - unchanged from before the extraction, not something this migration added or was asked to fix.
- **`splashgate-wrapper`**: `_layout.tsx`'s `GatedApp` now renders `@tastic/core`'s new `<SettingsAndProfilesGate Gate={SplashGate} settingsLoaded={settingsLoaded} profilesLoaded={profilesLoaded}>` instead of two separately-named local components this app previously called `SettingsReadyGate`/`ProfilesReadyGate`. Unlike Snake (the one app with a dedicated `Theme.test.tsx` that mocks `@rific/auto-paper`'s module factory and needed that mock updated to also export `useThemeBridgeProps`), this app has no direct test coverage of `Theme.tsx`, so nothing broke mechanically here - also nothing confirms the swap preserved behavior beyond a manual/visual check.

## Settings and Lock Orientation (2026-10-07)

**Settings live in Redux**, like every other persisted value: `src/redux/settingsSlice.ts` (`DEFAULT_SETTINGS` plus `@rific/core`'s `createSettingsSlice('settings', { initializeMode: 'merge' })`), read and written only through `useSettings()` (`src/hooks/useSettings.ts`, returning `{ settings, setSettings(patch) }`). There is no validation and no migration: the factory's REHYDRATE handling fills any field added since a player's settings were saved from the defaults. Settings saved by older builds under the old AsyncStorage settings key were deliberately abandoned (Jay, 2026-10-07). `PersistGate` (in `Providers.tsx`) holds rendering until the store has rehydrated, so there is no settings splash gate; `_layout.tsx`'s `GatedApp` waits only on profiles. This replaced `@tastic/core`'s `createGameSettingsProvider`/`GameSettingsProvider`/`useGameSettings` and the per-game `isValidSettings`.

- **Per-round state** lives in `src/redux/liveplaySlice.ts`, blacklisted from persistence in `store.ts`: `activeRoundSettings` (the snapshot the loadout commits when every human player readies up, so a mid-match settings change only affects the next match) and `activelyPlaying` (written by `/game`, read by `Providers.tsx`'s `EdgeGuardBridge`, the only `useEdgeGestureGuard` call).
- **Lock Orientation** is app-wide via `@tastic/core`'s `OrientationProvider` `freezeWhileLocked`, wired in `_layout.tsx`'s `OrientationBridge`. While locked, the ONE shared orientation reading freezes for every consumer: every screen's `useOrientationState()`/`useRotation()`/`FakeLandscapeView`, the in-game board (touch mapping included), hud dialogs, `GuideHost` and the status bar (`useRotationAwareStatusBar`), including anything that mounts after the lock. Never hand the setting to a call site (`useOrientationState(x)`, `useRotation(x)`, `<FakeLandscapeView locked>`, `useRotationAwareStatusBar({ locked })`): a per-call-site lock freezes on the pre-sensor portrait default at mount, which is the relaunch bug this replaced.
- **`lockedRotation`** (optional `ViewRotation` on `Settings`, absent from `DEFAULT_SETTINGS`): the locked angle, recorded by `onLockChange` on lock and cleared on unlock, never set by UI. Handed back through `lockInitialValue`, it makes a relaunch open in the locked orientation from the first frame. The Settings dialog toggle only writes `lockOrientation`; the provider adopts the changed `lockInitialValue` after mount (`@rific/core` 0.3.0+) and reports the angle back, so it applies immediately, mid-match included.
- **Byte-identical across AirHockey, BoxHockey, LightCycles and Pong:** `_layout.tsx`, `liveplaySlice.ts`, `achievementsSlice.ts`, `useSettings.ts`, `settingsSlice.test.ts`, `Providers.tsx`'s `EdgeGuardBridge`, everything in `settingsSlice.ts` except `DEFAULT_SETTINGS`, and this section. ## Background pause, profile prune, control scheme swaps, rink containment (2026-10-08)

- **Background pause (F085):** `game.tsx` calls `@tastic/core`'s `useBackgroundPause`. Any AppState change away from `'active'` mid-match (home, app switch, a call, iOS `'inactive'` for Control Center; a hidden tab on web) latches `backgroundPaused`, which is ORed into `paused`, so the game loop, the idle/goalScored serve pause, the CPU, both input layers and Edge Guard stop exactly as they do for an open dialog. It never latches at game over or while Settings or Quit Match? is already open. The latch survives the return: a 'Paused' `ConfirmDialog` (same `rotationDeg` and `progressMessage` score line as Quit Match?) offers Resume, which clears it and restarts the serve pause from scratch, or Quit (`safeBack`, no second confirmation). The hook call and the Paused dialog are the same text in AirHockey, BoxHockey, LightCycles, Pong and Snake.
- **Profile prune:** `useProfiles.tsx` dispatches `@tastic/profile`'s `profileSelectionActions.pruneToRoster(ids)` after both `setAll` calls (the initial reconcile and `onRemoteChange`), so a seat never keeps pointing at a profile a sibling app deleted (its results would land under a ghost id). Unchanged prunes return the same state. Stats of deleted profiles and seat color overrides are deliberately left alone: a transient empty shared-store read would otherwise erase real data. Tested in `useProfiles.test.tsx` against a fake App Group module.
- **Control schemes:** both loadout pickers write through @tastic/input's assignSeatScheme (swap on conflict: picking the other seat's scheme hands it this seat's old one), so the two seats never share a scheme. Without it a 1 Player pick of seat 2's scheme left both seats on it, and KeyboardInputLayer sent every one of those keys to seat 1 in a later 2 Player game. The guide's old `effectiveSchemes` copy workaround is gone.
- **Rink containment (F061):** `physics.ts`'s outer back wall uses BoxHockey's `skipGoalGap` (`board.behindGoalDepth > 0`, true whenever Settings.rink is on), so it's solid across the full width behind each goal, goal mouth and post strips included. It used to have a hole there: a puck that bounced off the one-way door, or slipped past a post into the pocket, kept its speed (behind-the-line pucks skip friction) and left the rink for good. Only a pocketless board (Settings.rink off) keeps the open mouth. Tested in `physics.test.ts` (door bounces held in the pocket for 300 steps, and a 300-step angled-shot sweep with real posts and 0 escapes).
- **Stranded puck re-serve:** with the wall solid, a puck with little sideways speed rattles between the door and the back wall, losing `WALL_RESTITUTION` on every bounce, and can stop behind the line where no paddle reaches (`clampToOwnHalf`). `useGameState`'s TICK re-serves it when `stepPhysics` reports `stopped` while the puck is fully behind a goal line (`pocketSide`): no goal, the puck goes to the nearer `faceoffZoneCenter` in that end (top pocket = player 2's end, GOAL_SERVE's mapping) and the phase drops to `'idle'`, so the usual `GOAL_SERVE_PAUSE_MS` beat runs before `START`. BoxHockey doesn't need this: a stopped puck ends the turn there. A puck that crawls just above `STOP_THRESHOLD` behind the line is not re-served until it stops; a scratch sweep over real layouts found that can take over a minute on a large-puck tablet board (rare, but a dwell limit would be Jay's call).
- **One door hit per pocket visit:** `GameState.pocketDoorHit` latches the side whose door the puck already hit while it stays fully behind that line, so the rattling only counts once toward `goalDoorHitCount` (the Ring the goal door stat and Board's flash). Cleared when the puck leaves the pocket, scores, or is re-served. Tested in `useGameState.test.ts` (both pockets re-serve at rest with no goal and exactly one door hit, and a later visit counts again).
- **Unreleased packages:** `useBackgroundPause` (planned `@tastic/core` 0.12.0), `pruneToRoster` (`@tastic/profile`, after 0.10.0) and `assignSeatScheme` (`@tastic/input`, after 0.3.0) were installed from local tarballs with `npm install --no-save`. `package.json` ranges still need bumping to the released versions before these changes are committed: on the published ranges a fresh `npm ci` fails tsc and jest.

## Rink toggle (2026-10-14)

`Settings.rink` (default `true`) is BoxHockey's rink toggle with BoxHockey's exact geometry, replacing the old always-on rink and the single-option `mapMode` stub (removed; a stale persisted `mapMode` key is harmless). On: rounded corners and a pocket behind each goal (`cornerRadius`/`behindGoalDepth`), with the depth floored at both long-axis safe-area insets and borrowed from them, so the pocket reaches the physical screen edge and the goal lines stay at the safe-area edge instead of being pushed forward. With unequal insets (notch vs. home indicator) or an inset smaller than the puck-clearance minimum (`2.5 * puckRadius + WALL_THICKNESS`, about 67 on a 393pt iPhone at medium puck), the goal line sits in from its edge by the difference, same trade-off as BoxHockey. Nothing is drawn for the corners or the pocket boundary (`SHOW_RINK_DEBUG_PERIMETER` in `Board.tsx` draws them for tuning), and desktop perimeter walls only show with the rink off. Off: square corners, no pocket, permeable goal line at the safe-area edge, goal lines in the neutral wall color, no door flash. To let the pocket reach into the insets, `game.tsx`'s board container now covers the whole screen (`computeLocalContainerSize` takes no insets) and `computeBoardLayout(..., rink)` keeps the field inside the safe area itself. The loadout's Board trigger holds just the Rink toggle (BoxHockey's `RINK_OPTION`). Not checked on a native device or simulator yet; the inset math is covered by `boardGeometry.test.ts`.

## OS portrait lock (2026-10-08)

The OS is locked to portrait on every device and the app draws all rotation itself (`@tastic/core`'s `OrientationProvider` reads the accelerometer). `@tastic/core`'s Expo config plugin (`"@tastic/core"` in `app.json`'s `plugins`) owns every native setting that depends on: `orientation: "portrait"`; `ios.requireFullScreen` plus a Portrait-only iPad orientation list (audit F009: without it Expo forces all four iPad orientations, so iOS turned the screen on top of the app's own rotation, and Split View, Slide Over and Stage Manager are the price); and `android:appCategory="game"` (Android 16 and later ignore the portrait lock on tablets and unfolded foldables, except for games). Don't set any of those by hand here, and don't add `expo-screen-orientation` (it re-enables upside down on home-button iPhones). The why behind each is in @tastic/core's README. Check the result with `npx expo config --type introspect`; it only takes effect in a new native build.

## Status bar: per-screen options (2026-10-15)

The OS status bar is set through react-native-screens' screen options, never a `StatusBar` component. `_layout.tsx`'s `AppStack` (identical across AirHockey, BoxHockey, LightCycles and Pong) spreads `@tastic/core`'s `useRotationAwareStatusBar()` (0.14.0+) into the root Stack's `screenOptions`, which hides the bar while the content is rotated off portrait (no `locked` argument: `OrientationBridge` freezes the reading it follows), and /game hides it for the whole round through its own `Stack.Screen` options (`GAME_OPTIONS`, `{ statusBarHidden: true }`), set in the layout so they apply as the screen is pushed rather than one effect later. No style is passed: react-native-screens' default (`auto`, following the system appearance) is what expo-status-bar's `auto` gave before.

Why: an app linked against the iOS 27 SDK (Xcode 27) can't set the status bar through `UIApplication` any more (UIKit's `UIApplication.h`: setting it "does nothing if ... linked against SDK versions 27.0 or later"), and that is all React Native's `StatusBar`, and so expo-status-bar, does on iOS. `@tastic/core`'s config plugin now sets `UIViewControllerBasedStatusBarAppearance: true`, which react-native-screens needs, and under which every mounted `StatusBar` logs an `RCTLogError` (a red box in dev). So nothing may mount one: `<RotationAwareStatusBar />` (removed from core) and /game's `<StatusBar hidden />` are gone, `Theme.tsx` passes auto-paper's Provider `statusBar={false}` (0.13.2+, which also covers `Appbar.Header`), and expo-status-bar is no longer a dependency or an app.json plugin (its plugin did nothing without options). Pinned by `src/__tests__/statusBar.test.tsx` (no source file imports expo-status-bar or React Native's `StatusBar`; Theme turns auto-paper's off).

- **The hide only shows in a Release build.** In a dev-client (development) build, expo-dev-launcher inserts its own view controller above react-native-screens' stack, so the screens' status bar options never reach UIKit and the bar never hides there, rotated or on /game (see @tastic/core's CLAUDE.md, "Status bar: per-screen options"). Check it in a preview/production build or a local Release build.
- **It needs a new native build.** `UIViewControllerBasedStatusBarAppearance` only reaches Info.plist at prebuild, and the app.json plugin list changed too, so the fingerprint runtime version moves on: an OTA update from here on won't reach an older binary.
- Android gets the same options from react-native-screens (no Info.plist key there). Not checked on a device on either platform.

## Xcode 26 image pin (remove on Expo SDK 58)

`eas.json` pins the `preview` and `production` iOS builds to `macos-tahoe-26.5-xcode-26.6` (set fleet-wide 2026-10-14). An app linked against the iOS 27 SDK aborts at launch on iOS 27 ("UIScene life cycle is required for apps built with this SDK") unless it adopts the UIScene life cycle, which SDK 57's native template doesn't do and SDK 58's does. A build made with Xcode 26 runs fine on iOS 27. **When this app moves to Expo SDK 58, remove both `ios.image` pins and this section**, so builds go back to EAS's default image for the SDK. Local builds (`eas build --local`, `expo run:ios`) ignore the pin and use this Mac's Xcode 27; `plugins/withSceneDelegate.js` (listed in `app.json`, added fleet-wide 2026-10-15) makes them run on iOS 27 by wiring SDK 57's own `ExpoAppSceneDelegate` the way SDK 58's template does: `AppDelegate` conforms to `ExpoReactNativeFactoryProvider` and stops creating the window and overriding the Linking methods, `Info.plist` gets the scene manifest, and `SceneDelegate.swift` joins the app target. It edits `AppDelegate.swift` last (a finalized mod, whatever the `app.json` order), keeps any lines other plugins add after `startReactNative` (`@tastic/edge-guard`'s `_ = tastic_edgeGuardSwizzle`), throws on anything else unexpected rather than half-apply, and does nothing on SDK 58+. **On SDK 58, also delete the plugin and its `app.json` entry.** Solitaire's CLAUDE.md records how it was verified.
